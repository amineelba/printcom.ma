# Architecture

## Overview

Printcom.ma is a single Next.js application with Payload CMS embedded via
`@payloadcms/next`. There is no separate backend service — the Next.js
app serves the public frontend, the Payload admin panel, and Payload's
REST/GraphQL APIs from one deployment.

```text
┌─────────────────────────────────────────────────────────────┐
│                      Next.js application                     │
│                                                                │
│  app/(frontend)/    Public site — Server Components by       │
│                      default, Payload Local API for reads    │
│                                                                │
│  app/(payload)/     Payload admin panel (generated)          │
│                                                                │
│  app/api/[...slug]  Payload REST API                          │
│  app/api/graphql    Payload GraphQL API                       │
│                                                                │
│  src/proxy.ts       Redirect resolution (runs before render)  │
└───────────────────────────┬────────────────────────────────┘
                             │
                    Payload Local API / Postgres adapter
                             │
                    ┌────────▼────────┐
                    │   PostgreSQL     │
                    └──────────────────┘
                             │
                    ┌────────▼────────┐
                    │  Media storage   │
                    │  (local disk in  │
                    │  dev, Vercel     │
                    │  Blob when       │
                    │  BLOB_READ_WRITE │
                    │  _TOKEN is set)  │
                    └──────────────────┘
```

## Why a single app instead of a headless split

The brief calls for one deployable unit with Payload "intégré à Next.js."
Server Components can call the Payload **Local API** directly
(`src/lib/payload/client.ts`) — no HTTP round-trip, no separate auth
token, and TypeScript types are shared end-to-end via
`src/payload-types.ts` (generated by `payload generate:types`). The
public REST/GraphQL APIs still exist (Payload always exposes them) and
are what a future headless client would use, but the frontend itself
never calls them.

## Route groups and parallel root layouts

`src/app/(frontend)` and `src/app/(payload)` are Next.js route groups,
each defining its own root layout (each renders its own `<html>`/`<body>`).
This is why `src/app/not-found.tsx` exists at the true root with its own
`<html>`/`<body>`: for a URL that matches neither group, Next has no
single parent layout to fall back to, and its own generic 404 would render
instead of Printcom's. `src/app/(frontend)/not-found.tsx` (which reuses
the full site chrome — header/footer) only catches explicit `notFound()`
calls made **from inside** a page in that group.

## Data access pattern

Every frontend page/route follows the same shape:

```ts
const payload = await getPayload()               // src/lib/payload/client.ts, memoized
const result = await payload.find({
  collection: 'products',
  where: { status: { equals: 'published' } },     // explicit filter, not relying on access control
  depth: 1,
})
```

Frontend queries **explicitly filter for `status: 'published'`** (and,
for technologies/machines/testimonials/clients, `verificationStatus:
'confirmed'`) rather than relying solely on collection-level `access`
rules. This is deliberate defense in depth: Payload's Local API defaults
`overrideAccess: true`, so access-control functions are not automatically
enforced against Local API calls unless you pass `overrideAccess: false`
explicitly. The actual enforcement boundary for anonymous users is the
public REST/GraphQL API (see `docs/access-control.md`), which does apply
access control by default. The frontend's explicit `where` filters mean
draft/unverified content never renders publicly even though the frontend
itself has full read power via the Local API.

## Rendering strategy

- Default: Server Components, ISR with a 5-minute `revalidate` set on
  `src/app/(frontend)/layout.tsx` (applies to statically-shaped pages;
  routes reading `searchParams`/`cookies()`/`headers()` — `/produits`,
  `/recherche`, `/demande-de-devis` — are automatically rendered
  per-request by Next regardless of this setting).
- Client Components are used only where interaction requires them:
  navigation disclosure, search overlay, filter bar, the quote wizard,
  file upload, accordions. Everything else is a Server Component.
- `src/proxy.ts` (Next 16 renamed "middleware" to "proxy"; it always runs
  on the Node.js runtime, which the Postgres adapter needs) resolves
  `redirects` collection entries before any route renders.

## Database and migrations

`payload.config.ts` sets `push: false` on the Postgres adapter: schema
changes are **always** migration-driven, in every environment, including
local dev. This was a deliberate fix — Payload's dev-mode automatic
schema push conflicted with an already-applied formal migration during
development and produced a broken `ALTER TABLE ... DROP CONSTRAINT`
error. After changing any collection/global's fields, run:

```bash
pnpm payload migrate:create <short-description>
pnpm payload migrate
```

and commit the generated files in `src/migrations/`.

## Media storage

`src/collections/Media.ts` defines five image sizes (thumbnail, card,
listing, hero, openGraph). Storage is local disk by default; setting
`BLOB_READ_WRITE_TOKEN` in the environment switches the `Media`
collection to Vercel Blob via `@payloadcms/storage-vercel-blob` (wired
conditionally in `payload.config.ts`) — no code change needed to move
from local dev to a Blob-backed deployment.
